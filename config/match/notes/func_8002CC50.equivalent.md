# func_8002CC50

Rasterises a transformed box into a 32-row table and marks the covered cells in the bitmap at `D_8005F3C4`.

- Builds the 8 corners of the box from `arg0`, transforms them with `func_8003EAD4`.
- For up to three levels (`arg1[1]`/`arg1[4]` clamped by `arg0+0x30`/`0x3C`, then their midpoint) clips the box with `func_8002FFFC`, giving `n` edges (2 points each).
- Bounding box of the clipped points is converted to a 32x32 grid (origin `arg2`, `(d*4)/8192 + 16`); boxes off the grid are skipped.
- Each edge is walked with Bresenham (horizontal, x-major, z-major) into a per-row `[min, max]` byte table (`-1..32` clamped).
  With `arg3 != 0` the walk also calls `func_8002CB1C` on cells in a window of -16..47, one per 8 steps, plus a pending last cell.
- Each row's span is then OR-ed into the bitmap as a mask.
- The return value is the leftover `v0` of the retail code (reject value, `n*2`, last row's mask); `ret` reproduces it.

## What still disagrees

- Every branch of the assembly has its counterpart in the C; the disagreements were not traced to a logic difference.
- `func_8002FFFC` is not run, so `pts` (retail `sp+0x78`) is read as uninitialised stack. When `n` is large the retail loop reads past `pts` into
  the rest of its frame; the candidate's frame layout differs, so those trials differ (changing the frame size moved the count between 410 and 459).
- Calls to `func_8002CB1C` show up in the candidate as a call to the file's own compiled definition (0x8040339c), not the retail address,
  so trials with flag != 0 that reach those calls are likely not comparable.
- Attempts: attempt1 (base, 459), attempt2/3 (single frame struct, 410/459), attempt5/6 (bigger `pts`, frame padding; 449, 410-459).
