# func_800394C4

Interpreter handler for a VM-style instruction word: decodes a source operand (register, stack pop, or via
`func_80036D0C`), a function index, and up to 7 stack arguments copied into a local array, then calls
`func_8001D1E0`. Afterwards it pops the stack (`0xBC`) by a field of the instruction, or returns -0xFF when
flag `0x20000` is set and `arg2 & 2`.

Not matched. Best: `best.c` (= attempt4.c), 99 of 112 words differ.

Findings:
- Frame size matches only with `s32 args[18]` (0x78).
- Prologue matches (`s3 = a2` early) when the instruction's `& 0xFFF` is held in a temporary.
- Still differs from the first branch on: retail computes `ins & 0xFFF` into `$a0` then copies to `$a1`; the compiled
  code computes it straight into `$a1`. The same applies to the 6-bit register index (retail keeps it in `$a0`, and
  tests it against 0x1F through `$v0`/`$v1` in a different order). Every later word is shifted by the resulting
  size/order differences, so the rest of the diff is probably small once these two are fixed.
- Tried: `s32`/`u32` temporaries, if/else-if reordering of the operand decode; none lowered the count.
- Next: try permuter on best.c, or hold the two decoded fields in variables declared before `fn`.
